# 기능 TC 프레임워크를 만들어서 개발 속도를 올린 이야기

## 문제: 새 기능 하나 넣을 때마다 불안하다

운영 중인 Form 서비스가 있다. 설문 생성, 편집, 설정, 응답 수집, 결과 조회, CSV 다운로드... 기능이 꽤 많다.

새 피처를 개발할 때 제일 시간이 걸리는 건 **코딩이 아니라 영향 범위 파악**이었다. "익명 설정 로직을 바꿨는데, 이게 응답 수정이나 결과 조회에 영향을 안 줬나?" — 이걸 확인하려면 관련 코드를 하나하나 grep하고, 테스트를 돌려보고, 그래도 뭔가 빠뜨린 건 아닌지 불안한 채로 배포했다.

테스트 코드는 있었다. 하지만 **클래스별로 존재하는 테스트**였다. `FormSettingServiceTest`, `AnswerServiceTest`, `FormResponseServiceTest`... 각 서비스 클래스의 메서드를 검증하는 테스트. 코드 커버리지는 올라가지만, 이게 **기능을 검증하는 건지**는 별개 문제다.

### 코드 커버리지 vs 기능 커버리지

기존 테스트가 놓치고 있던 건 이런 거다:

```
"익명 폼에서 응답 수정이 허용되면 안 된다"
→ FormSettingService에서 익명 설정할 때 차단하는 테스트는 있는가?
→ AnswerService에서 수정 시도 시 차단하는 테스트는 있는가?
→ FormResponseService에서 응답자 이름이 안 보이는 테스트는 있는가?
→ CSV 다운로드에서 익명 컬럼이 적용되는 테스트는 있는가?
```

**하나의 기획 스펙이 4개 서비스에 걸쳐 있다.** 클래스별 테스트만으로는 "이 기능이 전체적으로 검증되고 있는가?"를 알 수 없다. 어떤 클래스에는 테스트가 있고, 어떤 클래스에는 빠져 있어도 티가 안 난다.

그래서 원했던 건 이거다:

> **"폼의 모든 기능에 대한 TC가 있는지 한눈에 확인할 수 있는 체계"**

단순히 커버리지를 높이는 게 아니라, 기획 스펙 하나하나에 대응하는 TC가 있는지 — 그리고 그 TC가 어떤 테스트 코드로 검증되고 있는지 — 추적 가능한 구조.

### 그런데 기획 스펙이 정리된 게 없었다

문제는 **"폼의 모든 기능"이 뭔지를 정의한 문서가 없다**는 거였다. 기능이 추가될 때마다 Dooray 업무에 요구사항이 흩어져 있고, 코드를 까봐야 "아 이런 예외처리도 있었구나" 하는 식이었다.

기존 클래스별 테스트를 버리자는 게 아니다. 코드 커버리지는 코드 커버리지대로 유지하되, 그 위에 **기능 스펙 기반의 TC 체계를 얹어서** 두 가지를 동시에 만족시키고 싶었다:

1. **기획 스펙을 전부 정리한다** — 폼이 지원하는 모든 기능을 TC로 나열
2. **각 TC를 실제 테스트 코드와 연결한다** — 이 기능에 대응하는 테스트가 있는지, 빠진 건 없는지 추적 가능하게

## 접근: 기획 스펙 문서를 코드와 양방향으로 연결하자

기획 스펙을 정리한 문서를 만들기만 하면 금방 낡는다. 코드와 동기화되지 않는 문서는 결국 아무도 안 보게 된다. 그래서 **스펙 → 테스트 코드 → 스펙** 순환이 자연스럽게 돌아가는 구조를 설계했다.

```
TC_FULL_SPEC.md ←──→ @TC 어노테이션 ←──→ 테스트 코드
     (스펙)            (시맨틱 ID)           (검증)
```

### 핵심 아이디어: 시맨틱 ID

TC 번호(TC-001, TC-002...)는 순서가 바뀔 수 있다. 중간에 TC를 추가하면 뒤의 번호가 전부 밀린다. 그래서 **번호와 별개로 의미 기반 ID**를 부여했다.

```
TC-071 → SETTING_ANON_PUBLIC_FIXED
TC-072 → SETTING_ANON_PUBLIC_MODIFY_BLOCK
TC-076 → SETTING_ANON_ACTIVATED_LOCK
```

TC-071이 TC-072로 재번호되어도, `SETTING_ANON_PUBLIC_FIXED`라는 시맨틱 ID는 **절대 변하지 않는다**.

테스트 코드에는 이 시맨틱 ID를 어노테이션으로 붙인다:

```java
@TC("SETTING_ANON_PUBLIC_FIXED")
@Test
void publicFormAnonymousOptionShouldBeFixed() {
    // given: 내·외부 공유 폼
    // when: 익명 설정 변경 시도
    // then: 변경 불가 (PUBLIC은 익명 고정)
}
```

이제 **TC 번호가 재번호되어도 테스트 코드는 수정할 필요가 없다.**

## 구조: 서비스 라이프사이클 기반 Part 분류

TC를 어떻게 분류할지가 제일 중요했다. 기능별? 화면별? API별? 고민 끝에 **서비스의 핵심 라이프사이클**을 기준으로 잡았다.

```
생성 → 편집 → 설정 → 게시/상태 → 공유/접근 → 응답 → 결과 → 관리 → 부가기능
```

이 9단계가 곧 Part 1~9가 된다. 새 기능이 추가되면 이 플로우 중 어디에 해당하는지로 자연스럽게 배치가 결정된다.

| Part | 카테고리 | TC 수 |
| :--- | :--- | :--- |
| Part 1 | 폼 생성 | 14 |
| Part 2 | 폼 편집 | 47 |
| Part 3 | 폼 설정 | 36 |
| Part 4 | 게시/상태 | 10 |
| Part 5 | 공유/접근 | 9 |
| Part 6 | 응답 | 17 |
| Part 7 | 결과/CSV | 17 |
| Part 8 | 폼 관리 | 29 |
| Part 9 | 부가 기능 | 22 |
| **합계** | | **201** |

## 네비게이션: 스펙 ↔ 코드를 자유롭게 오가기

201개 TC가 있으면 원하는 TC를 찾는 것 자체가 일이다. 그래서 **양방향 네비게이션**을 만들었다.

### 1. 매핑 테이블 → 상세 TC (앵커 링크)

매핑 테이블의 TC 번호가 클릭 가능한 링크다:

```markdown
| [TC-071](#tc-071) | `SETTING_ANON_PUBLIC_FIXED` | 익명 옵션(내·외부) 고정 |
```

클릭하면 해당 TC의 상세 설명(절차, 기대결과)으로 점프한다.

### 2. 상세 TC → 테스트 코드 파일 (📍 코드 링크)

각 TC 상세 섹션에서 실제 테스트 코드로 바로 이동할 수 있다:

```markdown
### TC-071: 익명 옵션(내·외부) 고정
`@TC("SETTING_ANON_PUBLIC_FIXED")` · ↑ 목차
· 📍 Unit:Part3_AnonymousSettingServiceTest · Intg:Part3_AnonymousSettingTest
```

📍 뒤의 링크를 클릭하면 Unit 테스트, Integration 테스트 파일로 각각 이동한다.

### 3. 테스트 코드 → TC 스펙 (grep)

테스트 코드에서 스펙 문서로 돌아가고 싶으면:

```bash
grep -n 'SETTING_ANON_PUBLIC_FIXED' TC_FULL_SPEC.md
```

**세 방향 어디서든** 원하는 정보로 바로 도달할 수 있다.

## 코드 링크 자동 갱신

TC를 추가하거나 테스트 파일이 리팩토링되면 📍 코드 링크가 깨질 수 있다. 이걸 수동으로 관리하면 금방 지친다.

그래서 **자동 갱신 스크립트**를 만들었다:

```bash
python3 update_tc_links.py
```

이 스크립트는:
1. 프로젝트의 모든 `@TC("...")` 어노테이션을 grep
2. 시맨틱 ID → 파일 경로 매핑을 자동 수집
3. TC_FULL_SPEC.md의 📍 코드 링크를 갱신

TC를 추가한 후에 한 번 실행하면 끝이다.

## AI와의 협업: TC 추가 가이드

이 프레임워크의 실제 사용자는 나만이 아니다. **AI(Claude)가 테스트 코드를 생성할 때**도 이 형식을 정확히 따라야 한다.

그래서 TC_FULL_SPEC.md 안에 "AI 작성 가이드" 섹션을 넣었다. TC를 추가할 때 반드시 수정해야 하는 **4곳**과 **체크리스트 8항목**을 명시해놨다.

```
TC 추가 시 필수 작업:
1. 매핑 테이블에 행 추가    [TC-{번호}](#tc-{번호})
2. 상세 TC 섹션 추가        <a id="tc-{번호}"></a> + 📍 링크
3. 테스트 코드에 @TC 추가    @TC("{시맨틱_ID}")
4. 목차 TC 범위 업데이트     TC 수 갱신
```

이렇게 해두니까 AI가 TC를 추가할 때 **형식이 깨지지 않는다.** "TC-202 추가해줘"라고 하면, 매핑 테이블, 상세 섹션, 테스트 코드, 목차까지 4곳을 한 번에 수정해준다.

## 다른 프로젝트에서도 쓸 수 있게

이 구조가 Form 서비스에만 국한될 이유가 없다. **Part 구조만 바꾸면** 어떤 서비스든 적용할 수 있다.

범용 템플릿 패키지를 만들었다:

```
tc-framework/
├── TC_SPEC_TEMPLATE.md    # 스펙 문서 스켈레톤
├── TC.java                # @TC 어노테이션
├── TCs.java               # @TCs 컨테이너
├── update_tc_links.py     # 코드 링크 자동 갱신
└── README.md              # 적용 가이드
```

프로젝트별 Part 구조 예시:

```
# 메신저 서비스
인증 → 채널 → 메시지 → 스레드 → 멘션 → 파일 → 검색 → 알림 → 관리

# 메일 서비스
작성 → 발송 → 수신 → 검색 → 폴더 → 필터 → 첨부 → 설정 → 관리

# 일반 CRUD API
생성 → 조회 → 수정 → 삭제 → 검색 → 권한 → 알림 → 관리
```

새 프로젝트에 적용하는 과정:

1. 템플릿 4개 파일 복사
2. `TC.java`의 패키지명 수정
3. `TC_SPEC_TEMPLATE.md`의 Part를 서비스 라이프사이클에 맞게 재정의
4. TC 작성 시작

## 실제 효과

201개 TC를 정리한 후 체감한 변화:

**스펙 확인 시간 감소**: "익명 폼에서 응답 수정이 되나?" → TC_FULL_SPEC.md에서 `SETTING_ANON` 검색 → TC-071~079에서 바로 확인. 코드를 뒤질 필요가 없다.

**새 기능 추가 시 영향 범위 파악**: "익명 설정 관련 코드를 바꿔야 하는데 어디어디 영향이 있지?" → Part 3.4의 TC 9개를 보면 설정 변경, 게시 후 제한, 식별정보 미수집 등 모든 케이스가 보인다.

**테스트 코드 작성 속도**: TC 스펙에 절차와 기대결과가 명시되어 있으니, AI든 사람이든 테스트를 작성할 때 "뭘 검증해야 하지?" 고민이 사라진다. `@TC` 어노테이션으로 커버리지도 한눈에 파악된다.

```bash
# 구현된 TC 수 확인
grep -rh '@TC("' src/test/ --include="*.java" | sort -u | wc -l
# → 204 (일부 TC가 여러 테스트에서 검증되므로 201보다 많을 수 있음)
```

**QA 체크리스트 자동 생성**: TC_FULL_SPEC.md의 [FE]/[BE] 기대결과가 그대로 QA 체크리스트가 된다. 별도 문서를 만들 필요가 없다.

## 정리

| 요소 | 역할 |
| :--- | :--- |
| TC_FULL_SPEC.md | 전체 기능 스펙 + TC 목록 (Single Source of Truth) |
| 시맨틱 ID | TC 번호와 독립적인 불변 식별자 |
| @TC 어노테이션 | 테스트 코드 ↔ 스펙 연결 고리 |
| 📍 코드 링크 | 스펙 → 테스트 코드 원클릭 이동 |
| update_tc_links.py | 코드 링크 자동 갱신 |
| AI 작성 가이드 | TC 추가 시 형식 유지 보장 |

**"스펙 문서는 금방 낡는다"**는 편견이 있는데, 코드와 양방향으로 연결해두면 얘기가 달라진다. 테스트가 스펙을 검증하고, 스펙이 테스트의 존재 이유를 설명한다. 이 순환이 돌아가면 둘 다 살아있는 문서가 된다.
